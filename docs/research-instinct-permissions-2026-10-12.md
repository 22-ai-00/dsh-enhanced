# Instinct 的授权方式与 DSH 借鉴

**核查日期：**2026-10-12。仅依据 Instinct 官网和官方政策的公开文本；未获得产品账号，也未验证登录后的权限界面或实际审批频率。其条款和隐私政策均标注 2026-08-26 修订，使用政策标注 2026-08-20 修订。

## 可确认的产品事实

- Instinct 是 Spear Street Technology, Inc. 的个人助理。官网称用户可通过短信或电话交办，它可使用电话和电脑，示例包括争议账单、送礼、订杂货和安排就诊。这些是官方宣称的能力，官网没有公开逐项执行记录或实现细节。[官网](https://instinct.com/)；[隐私政策](https://instinct.com/privacy-policy)。
- 条款把用户提供或通过连接服务提供的内容视作输入，授权助理据此生成回复或采取行动；对已连接服务，授权涵盖访问、索引和交换数据，以及代用户采取行动。条款也涵盖代用户购买、订立协议或确认第三方条款。可确认的是产品采用**事先连接与授权、随后在授权范围内代办**的模型；公开条款不能证明每类动作都免于即时确认。[服务条款 §3](https://instinct.com/terms)。
- 隐私政策称助理可依用户授予的权限读取连接应用、消息、邮件、文件、语音、位置、付款或账户凭据等信息，利用交互和既往使用经历理解任务并给出个性化建议。官方明确列出 Google Calendar、Gmail、Drive、Docs、Sheets、Slides 和 Tasks，并提供断开连接及删除已索引数据的途径；断开连接本身不自动删除既有索引。[隐私政策：使用、Google Workspace、外部来源](https://instinct.com/privacy-policy)。
- 官方没有把自主行动描述为无限授权：条款保留对某些动作设置确认要求或其他控制的可能性，并要求用户审视动作与服务权限；隐私政策提示自主行动可能造成意外付款、对外通信或受第三方误导。使用政策也禁止未经授权的账户或系统访问。[服务条款：风险与责任](https://instinct.com/terms)；[隐私政策：数据安全](https://instinct.com/privacy-policy)；[使用政策](https://instinct.com/acceptable-use-policy)。

## 公开资料的边界

官方公开页面没有给出实际的逐动作审批矩阵、哪些动作默认无需确认、连接器 OAuth 具体 scope、授信的额度和时长、撤销传播延迟、审计与回滚机制，或后台主动任务的技术实现。因此不能断言 Instinct「完全不审批」或推断它让助理获得主机 root 权限。官网展示的任务示例也不是完成率或可靠性证据。[官网](https://instinct.com/)；[服务条款](https://instinct.com/terms)。

## 对 DSH 的直接启发

用户要的是一次性授予**持久但有边界的代理权**，让助理在已授权的任务、账户、动作、预算和时间范围内持续执行，完成后报告结果；超出授权范围、不可逆或受监管的动作再问。把每一次普通读取、构建、查询、重复任务都升级成人工审批，会打断这种体验。授权应绑定真实主人身份和当前会话，显示可查看、修改、撤销的清单；决策和结果留下审计记录。对外发送、支付、删除等动作可分别设置额度或对象范围，而不是把风险完全压到一个全局开关。

DSH 已有可用的权限基础：`assistant-policy` 的三档即时审批包含显式 `danger-full-access + never + none`，其参数级审批分支会直接放行，但独立 `tools.guard()` 继续约束身份、规则和预算。Auto 档已自动通过普通前台 Bash，却仍会让复杂或敏感命令进入额外审核。[策略服务](../plugins/assistant-policy/src/service.ts)；[风险分类](../plugins/assistant-policy/src/tool-risk.ts)；[三档说明](../plugins/assistant-policy/README.md)。因此优先把「已授权任务内的常用动作」从反复提示改为明确可持久化的细粒度授权，校准误报，并把真实授权状态清楚呈现给用户。单纯开启全机访问仍不足以提供连接器授权、持续任务、观察和撤销等助理能力。

源码的 Personal Assistant patch 已把新会话默认设为 full；用户 Settings 和既有会话事件优先，不会随重启或升级自动扩大旧会话权限。Delivery 已提供 `/permission full confirm`，无需重新发明一个关闭逐次工具审批的开关。它也不会自动开启后台 scheduler 或给予插件采用权。[默认配置](../plugins/personal-assistant/cordis.patch.yml#L13)；[安装设置保留逻辑](../scripts/install/common.sh#L2311)；[会话权限入口](../plugins/assistant-delivery/src/agent-runtime.ts#L917)。这是源码事实，不是本轮对运行中会话的核验。

## 建议的交付顺序与验收（尚未实现）

1. **先把主人授权接通，而不是继续加命令白名单。** 初次配对时提供清楚的高自主配置，持久记录可用目录、账户、后台任务和额度；已有会话通过受信任的权限入口迁移并回读真实生效状态。用户选择应可跨重启恢复，但不静默覆盖其他会话明确选择的较低权限。系统管理员权限是单独能力，不应把普通助理访问与任意 sudo 混为一谈。
2. **已委托事项内自主完成整条工具链。** 检索、下载、解析、写代码、安装依赖、运行测试及指定目录内整理不按每个命令重复询问；已授权的定时任务与学习继续运行。对指定收件人的通知、限定商户和额度的购买，也可以事先授权后直接完成；只在新增权限、越过额度或触及未授权的高影响事项时提问，问题用业务语言而不是展示一串 shell 命令。
3. **复用现有 Policy 和原生执行循环。** 前台权限、后台运行权、连接器权限和能力采用权分别明确接线；复用已有受信工具 preauthorization 和有限 action broker，不让模型或生成的插件自行改授权。发起工具调用与实际产生效果处都核对可撤销授权，保留预算、停止、审计和可用的回滚；不可逆动作不能承诺可以回滚。[现有预授权接口](../plugins/assistant-policy/README.md#finite-action-broker-preauthorization)。
4. **高自主不等于用文字规则假装隔离。** 任意宿主 shell 一旦能读取凭据并联网，工具名规则不能可靠限制它代发消息或付款。需要强制边界的账户和资金操作应经凭据代理/连接器执行；通用代码放在专用用户或隔离执行环境，不能宣称 full-access 本身提供这种限制。网页、邮件和工具输出是任务资料，不是新增授权来源。

验收按实际打断次数计：查资料并整理、授权目录内修代码、预先授权的后台任务在范围内均为 0 次逐工具审批；同一授权重启后无需重批。用新收件人、超额购买、撤权后排队任务和网页注入等负例验证边界；检查暂停能阻止尚未提交的后续副作用、失败不重复发送或扣款。不能只验证“审批框消失”，还应验证真实执行成功、结果留痕与异常通知。

本轮只研究并记录建议；没有修改运行时权限、扩大 sudo、启用任务或授予交易权限。
