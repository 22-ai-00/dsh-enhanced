# PTC 执行模式与持续成长

研究日期：2026-11-07。来源：飞书文章《打造 Personal Agent（四）：从 ReAct 到 CodeAct》
（<https://my.feishu.cn/wiki/CYANw7pSNiEhVckqaNXcCS8inAh>，revision 356，本地快照见忽略目录
`docs/evidence/ptc-research-20261107/`），以及当前 Harness 的 `dsh-tools` PTC 实现
（`mode`/`presentAs`、`run_code`、生成 SDK、`@deepseek-ai/dsh-ptc-runtime-node`）。

本文说明 PTC 为什么与本项目的持续成长目标直接相关、它改变哪些实施顺序、以及落地边界。
实现状态与剩余工作以 [RSI 当前状态](rsi-status.md) 为准；本文只保留设计判断。

## 文章主张（提炼）

- **ReAct → CodeAct Loop**：ReAct 让模型在每两个工具之间重新决策，中间结果进入上下文；
  PTC 让模型为一个阶段生成程序，程序在受控运行时里调用工具，自己完成并发、过滤、聚合、
  重试和错误分类，只把压缩后的结构化结果交回模型。差别是「谁负责控制重复的中间步骤」。
- **适用边界**：控制流已经稳定的阶段适合 PTC（计算/数据分析、并行多源查询、去重排序分页、
  固定顺序调用+有限重试、稳定模板填充）；每一步都改变语义判断、需要审批或外部副作用、
  必须保留原始引用/原生产物、页面或数据结构尚未探索时，保留直接 Tool Calling。
- **收益不只 Token**：中间结果留在程序里、并发关系明确、数据变换可单测、错误处理有固定位置、
  执行过程可回放。衡量至少要同时记录模型回合、输入/输出 token、工具调用数、端到端耗时、
  重试/失败恢复与最终质量；只看 token 下降会掩盖来源覆盖变差或错误恢复退化。
- **轨迹是 RSI 输入**：一次 PTC 执行留下代码、调用了哪些工具、哪些可并发、哪个步骤最慢、
  返回多少中间数据、重试几次、是否通过验收。RSI 流水线可以是：收集轨迹 → 找重复模式 →
  生成候选改动 → 用历史输入回放 → Evals 与小范围发布确认没有损害结果质量。
- **工具合并/拆分由真实调用统计触发**：总一起出现、输入输出边界稳定的动作合并为领域操作；
  职责过多、失败难以定位的工具沿轨迹拆分。不要凭感觉先设计大工具层。
- **渐进披露**：工具一多，模型负担首先是描述与 Schema。PTC 下只需一个可执行 JS 的工具入口，
  其余工具可按频率默认暴露或搜索后加载；披露策略本身可用轨迹统计优化。
- **两层隔离**：QuickJS 只隔离编排脚本，不自动隔离脚本调用的外部工具；真正的安全边界是
  宿主注入哪些函数、以及这些函数如何校验权限。已完成的工具调用不能因脚本后续失败而假装没发生；
  写操作默认要求显式确认或幂等键。

## 本项目对应关系

| PTC 概念 | 本项目现状 | 落地方式 |
| --- | --- | --- |
| 可预测阶段交给代码 | 后台工程作者固定执行 gaps→read→prepare→job_status；WorkItem 诊断是只读步骤序列；验收/学习是确定性流水线 | 对内部代理按需开启 PTC 呈现：一次模型回合写出编排脚本，嵌套工具调用不进上下文 |

## 分阶段落地

### 阶段 1（当前）：内部代理可选 PTC 呈现

- 对象：`assistant-growth-driver` 的后台成长代理（审计记录其真实模型任务曾因作者 5/7 次模型调用
  耗尽预算而失败）。PTC 下同一 wake 的 gaps→read→prepare→status 可压缩为 1 个模型回合。
- 开关：显式配置，默认 `native`（关闭时零行为变化）；缺少 `ctx.ptcRuntime` 时失败关闭并给出
  可操作错误，不静默回退。
- 约束：冻结的工具允许清单、schema 摘要、restrict、每 wake 工具调用上限、Policy 预授权、
  审批与输出上限全部保持；PTC 只改变模型看到的工具形态与执行编排，不扩大权限。
- 轨迹：运行结果只保留有界计数与摘要（`run_code` 次数、脚本字节/摘要、嵌套调用数/工具名计数/
  失败数/最长耗时），不保存脚本正文、参数正文或工具结果正文。

### 阶段 2：PTC 轨迹证据账本

- 在 owner-root 且已独立验证的完成目标上，从 session 事件提取 PTC 运行结构：
  每次 `run_code` 的脚本 digest/字节/语言、嵌套子调用（`<parent>:ptc:<n>`）的工具名序列、
  单次耗时、失败类别、重试、最终输出大小；任何正文都不入账。
- 通过 Host-only 只读接口提供给 Growth 作者（扩展现有 `growth_read_verified_workflow` 的投影），
  让它看到「同类任务历史上如何编排」，而不是只看工具名列表。
- 用轨迹统计形成工具合并/拆分与 skill/workflow 候选；候选仍走独立验收与有限采用，不由统计直接生效。

### 阶段 3：回放与同预算比较

- 版本化 workflow 候选 = 脚本 + 工具/参数 Schema 摘要 + 前置条件 + 期望证据。
- 回放使用冻结历史输入与只读/幂等工具；有副作用步骤必须带幂等键或转人工，禁止盲目重放。
- 比较父/候选：模型回合、工具调用、输入输出 token、端到端时延、重试、失败恢复、证据覆盖与
  独立质量验收；同一供应商、同一预算、保留失败样本，结论先标为观察性，符合门后才有限 canary。

### 阶段 4：渐进披露策略

- 用默认暴露工具的实际调用率、误选率、描述 token 与搜索命中率调整披露；披露策略作为可回放的
  workflow 版本管理，不写死。

## 指标

- 执行效率：模型回合数、工具调用数、端到端耗时、等待外部服务时间。
- 资源：输入/输出 token、脚本输出大小、重试次数与失败比例。
- 质量：事实正确性、证据覆盖、引用完整性、模板字段齐全、独立验收结论。
- 安全：写操作次数与审批覆盖、重放是否产生重复副作用、越权/秘密/错误外发保持零。
- 成长：候选→采用→改善→退役的完整周期；同预算前后对比；人工介入次数（拒绝率、漏报率、重复通知）。

## 边界

- PTC 不是安全边界；宿主的权限、预算、审批、输出上限、隔离与幂等键仍是权威。
- PTC 呈现需要部署挂载 `ctx.ptcRuntime`；未挂载的 profile 不得开启，默认关闭。
- 不把脚本正文、参数、工具结果正文写入账本；不把模型自评或轨迹相关性当作采用证据。
- 有副作用、需审批、需语义判断的步骤保留直接调用；PTC 只接管已经验证稳定的控制流。

## 与审计差距的关系

- P0-1（生产 intake 评估）：评估器本身可用一次固定模型调用实现；PTC 主要降低后续执行编排成本，
  不改变「模型判断 + 引文校验 + 预算」的确定性边界。
- P0-2（修订采用）：PTC workflow 是比纯工具更适合回放验证的制品，修订采用后可用同一回放集比较父/候选。
- P1-3（成长范围/后台复用）：后台工程与研究流程是最适合 PTC 的高频可预测流程。
- P1-4（证明后续更好）：PTC 轨迹提供可复现的回合/调用/时延/证据覆盖指标，是「同预算比较」的低成本来源。
