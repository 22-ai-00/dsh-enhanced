## 最短交付顺序

1. **完整仓库任务**：正式安装、现有模型、明确仓库/路径/次数/期限授权，真实事件进入原目标，模型自主调查和隔离修复，独立验收后提交允许分支/PR，重启后跟进 CI/评审并反馈。停止、过期、重复事件、未知提交结果和撤权必须沿同一条流程验证。测试仓库和凭据引用属于真实 GitHub 验收前置条件；本机闭环继续推进，但不得冒充远端验证。
   最先收口的交付门槛是普通请求 → 模型自行建立有限目标 → 隔离产物 → 独立验收 → 用户可见结果。通过后才继续集成仓库事件与 PR/CI，避免把多个尚未通过的环节一起调试。
2. **完整成长链**：成功/失败轨迹生成候选，独立留出、同模型同预算比较，受限推广，推广后 exact 版本退化回滚。将监控并入这一批，避免又产生只完善监控而无法推广的长期分支。
3. **扩展实际覆盖**：第二真实任务/日历来源、机会排序、3–5 类技能、记忆与策略的实际收益，补齐升级/卸载。相关工作包保持原验收要求。

### 仓库持续跟进的实际前置关系

对 `92abccf` 的只读审查确认，EventTriggers 的签名接收、持久来源序号，以及 Goals 的等待、重启唤醒均已存在；Actions 也已有 PR/checks/reviews 回读。接入 GitHub 时应复用这些接口，事件只表示状态可能变化，执行时重新读取远端。

但当前验收产物交付在整目标 achieved 后才创建 PR；此时原 Goal 已完成，CI/评审事件不能继续恢复它。因此，正式仓库授权入口之后的首要工作是让用户明确授权的**中间步骤交付**绑定独立步骤验收，而把**整个目标达成**绑定后续远端结果。应保留同一 Goal/Session、原有权限和不确定结果处理，再接 GitHub 信号。不能直接把当前已完成 Goal 的重启读回描述为持续 CI 跟进，也不应先新建 webhook 系统再发现该生命周期缺口。

另一个需随真实事件场景补齐的入口是来源 automation：EventTriggers 目标必须真实存在且 active，原事件测试使用了明确的测试观察执行器。生产接入应复用现有 Host executor 和调度预算提供无模型的来源观察能力；当前不存在的入口不能被测试替身掩盖。上述要求均保留在完整仓库维护验收中。

后续实施还须处理三个已有约束：原生目标回合的等待只能对准确已准入 run 开放受限 pause，不能直接移除 owner 检查；步骤回执持久化后需要一个仅用于重新核验的通知信号，不能挪用 Evaluation 的唯一回执消费者；现有无认证、固定对象的 `target-readback` 不足以独立验收私有 GitHub CI/评审，需认证且绑定实际提交的新鲜回读，截断结果必须保持 unknown。中间步骤交付应单独显式授权，旧 `verifiedDelivery` 的整目标验收要求保持不变；所有期限与预算须覆盖多次等待及最终验收。


### 中间交付与原生等待的接线结果

显式 `repositoryDelivery.acceptance: goal-step` 已经贯通正式配置、持久授权、模型授权发现和后台交付；省略时仍要求整体验收。新的 step artifact Host API 只证明准确已结束且 quiescent 的源步骤、当前 owner 与逐文件验收，不声称整个目标完成。Verifier 回执持久化后触发重新核验，启动时等待服务接通；暂时缺少验收读回不会提前把合法交付写成失败。

原生 admitted round 的 `goal_wait_event` 已接通受限暂停：没有人类回合也可在准确 run/revision 与已有权限下保存等待，成功才 conclude；存储失败记录 unknown，暂停后不能执行同批后续工具或继续模型请求。新增真实 AgentLoop/goal-round-driver/JSONL 测试覆盖这三个行为，Delivery、Policy、事件来源及模型仍是明确的测试替身。定向测试另证明 active 捕获交付意图后，原目标 paused、整体验收未达成时可按显式授权提交，并抑制重复执行。

下一步仍是同一仓库维护主线：把正式事件来源和认证的 CI/评审回读接入原目标，最终成功绑定实际提交 head 的新鲜结果。当前 WebOwner 配置只生成本地隔离产物验收；既有无认证固定对象 `target-readback` 不能冒充私有 GitHub 验收。上述接线不计为完整仓库维护或完整成长链完成，18 项范围保持不变。


## 本次复审的执行决定（基线 `e4044f5`）

主要瓶颈是已实现能力迟迟未冻结、生产组合的首次验证偏晚，以及外部前置条件没有与下一场景一起固定。继续拆出新组件不会缩短当前交付路径。本批冻结仓库新鲜验收和有限技能回滚两条已有实现，修复实际阻塞、独立复核、一次完整工程检查后提交；不把事件观察器、自动候选和推广继续追加进来。

下一批唯一主场景：明确仓库/分支/来源授权 → 步骤验收后 PR → CI pending 时等待 → Host 重启 → 一种仓库状态事件 → 原 Goal 恢复并重读准确 head → CI/评审达成 → 原会话反馈。优先把旧测试中的来源观察执行器换成正式 Host 配置，复用 EventTriggers/Automations，不扩多平台事件系统。事件本身不授予成功，实际远端回读仍负责验收；真实 GitHub 访问前置未满足时明确标记该场景未完成。

预算跟着这个场景核算：初始 branch read、commit、PR 共 3 次；每次新鲜验收另用 4 次动作。`maxActions: 7` 只足以一次 ready 回读，不能证明 pending 后还能继续。下一场景须显式限定允许回读次数并覆盖相应额度、目标轮次、等待期限与验证窗口，不能通过自动加额或固定提高一个最低数字保证无限跟进。

唯一独立辅助线继续 Skills 候选生成 → 独立比较资格 → 受限启用。当前比较明确记录 `heldoutIndependence: unproven`，有限回滚也不证明改进收益；封闭留出与晋升条件仍是硬前置。不得为主线的外部等待扩大辅助线到通用监控或另一套成长运行时。

子任务交接必须包含实际消费端调用的行为证据。本批 Actions 的直接调用虽通过，真实 Verifier→Cordis→Actions 调用却暴露对象绑定问题；修复后保留该集成断言。失败的集成用例不能通过删除来完成子任务。工程全检仍是交付门槛，开发中只运行受改动影响的检查；任何新增工作先指出它阻断上述哪个用户步骤。
