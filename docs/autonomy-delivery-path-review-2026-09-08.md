# 自治交付路径复审（2026-09-08）

结论：优先贯通正式安装后的完整用户能力，缩短首次真实集成的反馈周期。保留全部 18 项目标；取消按天和两周观察等待，不削弱权限、独立验收或回滚边界。

## 当前事实

复审基线为 `172c70f`。工作包账本为 3 项已验证、12 项实现中、3 项待做；工作量不同，不能换算成能力完成百分比。原有真实测试已证明事件恢复、隔离验收、技能复用和候选比较等局部流程，尚未证明完整仓库维护或自我改进收益。

本轮审查发现三类交付缺口：

- 正式安装组合遗漏事件、主动性、技能；目标配置只接受 DeepSeek 路线、要求手填 Session。现有可用网关没有进入正式入口。
- 既有真实测试按阶段限定工具、参数或结束回合，可以证明接线，却不足以证明模型能独立完成任务。新黑盒用例进一步发现模型无法查询已授权的隔离 grant ID，以及配置检查遗漏 `settings.yaml` 的模型选择覆盖。正式安装后首次实际任务还暴露了工具展示与执行权限不一致：模型多次选择 glob/bash/read 后被隔离守卫拒绝，耗尽实验调用额度，未建立 Goal。当前修复在正式产品中按 owner scope 展示可用工具，并解释原生有限目标入口，保持运行时授权检查。
- 仓库动作只有 commit。新加 branch/PR/readback 时另写生命周期，漏掉凭据等待后的撤权重查与卸载取消；原有测试通过未覆盖这些路径。独立复核还发现 reviews 数组被传输层拒绝、PR 仓库绑定不完整。它们均需具体修复与行为验证，不能以接口存在计为完成。

## 最短交付顺序

1. **完整仓库任务**：正式安装、现有模型、明确仓库/路径/次数/期限授权，真实事件进入原目标，模型自主调查和隔离修复，独立验收后提交允许分支/PR，重启后跟进 CI/评审并反馈。停止、过期、重复事件、未知提交结果和撤权必须沿同一条流程验证。测试仓库和凭据引用属于真实 GitHub 验收前置条件；本机闭环继续推进，但不得冒充远端验证。
   最先收口的交付门槛是普通请求 → 模型自行建立有限目标 → 隔离产物 → 独立验收 → 用户可见结果。通过后才继续集成仓库事件与 PR/CI，避免把多个尚未通过的环节一起调试。
2. **完整成长链**：成功/失败轨迹生成候选，独立留出、同模型同预算比较，受限推广，推广后 exact 版本退化回滚。将监控并入这一批，避免又产生只完善监控而无法推广的长期分支。
3. **扩展实际覆盖**：第二真实任务/日历来源、机会排序、3–5 类技能、记忆与策略的实际收益，补齐升级/卸载。相关工作包保持原验收要求。

## 执行调整

- 并行围绕一个主交付能力：产品入口与授权发现、仓库动作、真实验收。每个文件单一写者；依赖接口先对齐，独立部分立即并行。
- 最早运行普通任务输入。测试可以设置预算、私有验收条件并记录行为，不替模型选工具、填私有授权 ID 或规定工具顺序。
- 新动作复用已有持久预留、凭据租约、撤权、取消、未知结果流程，避免复制另一套控制逻辑。
- 子任务必须提交实际差异、新行为测试命令、退出码和输出；旧测试通过不能证明新路径。主协调整合后由独立验证者审查。
- 开发时定向检查；完整能力冻结后集中 `pnpm check` 和安装验收。失败先定位再复跑，不用反复全检代替定位。
- 交付报告区分“代码已实现”“实际验证通过”“已提交交付”。本复审和局部测试不会自动改变任何完整工作包的完成状态。
- 集成失败先归类为安装、线路、协议、决策或执行问题；只有具体修复或新假设才重跑。模型停止却没有 Goal 时应尽早报告失败，不持续等满实验时限。当前黑盒入口还没有这一提前退出能力，需在下一次实验前补齐。
