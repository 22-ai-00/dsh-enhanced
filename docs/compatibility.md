# 兼容性基线

基本 RSI 首版的已验证 Host 精确为 `@deepseek-ai/dsh@0.1.2-rc.1`。2026-09-12 的真实安装发现，全局 DSH `0.1.5-rc.1` 携带的 `dsh-session-persistence@0.1.5-rc.2` 不再提供 Policy 事件注册所需的 `PersistenceCoordinator.assertEventsSupported`，因此无法按当前可信注册协议激活。安装器固定匹配版本并在修改 profile 前拒绝其它版本；不会跳过事件证明或静默降级用户已有 CLI。扩展支持范围需完成独立的 Host 适配与真实安装验证。

Goals 的自动技能提取桥使用可选 Host peer `dsh-session-query@0.1.2-rc.1` 的 `observeSession(..., { projectionMode: 'none' })`，读取完成会话后释放 observation，不创建执行 Agent。缺少服务时返回 `unavailable`；Skills 在服务就绪后重新核验待处理授权。`verified-workflow-source/v1` 可附带只作来源记录、永不重放的 `failedObservations`，成功步骤语义不变。新 owner bridge 的多回合来源以可选 `segments` 保留连续执行记录，v1 顶层仍指向最终验收回合；既有手动单回合 API 不返回该字段。自动提取需成套升级 Goals 与 Skills；`skill_capture(start_native_rounds: true)` 仅在登记成功后使用原生 `concludeTurn()` 交接，默认仍允许同一 owner 回合组合授权。升级验证包括冷会话读取、授权撤销、失败观察隔离和真实目标交接后重启复用。

### WP17 supervised service-aware lifecycle（实现中，2026-09-11）

当前 WP17 实现 checkout-local 的 Linux `systemd --user`、installer-managed `supervised` profile upgrade 与 uninstall。两条路径都要求 Node.js、`flock`、Perl、固定的 `/usr/bin/python3`、bubblewrap、可用的 user manager，以及与用户 systemd 配置同文件系统的 canonical `DSH_HOME`。source profile 必须已经安装同一发行 cohort 中提供只读 Delivery owner、Recovery、Automations 与 supervised lifecycle/attestation seam 的版本；能力探测在 registry、Store 或 systemd mutation 前失败关闭，停服后的验证只读绑定快照，绝不通过打开 Store 触发迁移。

该切片使用 manifest v3，把原 active service 集、owner/配置/数据库摘要、preview nonce/catalog、guardian intent、post-swap attestation 和最终 `serviceAcceptance` 绑定为一个恢复协议。`serviceAcceptance` 必须精确覆盖原 active units、unit 唯一、数值字段为非负安全整数，且目标 unit 的 InvocationID 与 post-swap proof 一致；未知、缺失、重复、额外或 inactive 替代项都拒绝恢复。安装器只会屏蔽并停止经 HOME 与 WorkingDirectory 双重证明归属当前 home 的 units；归属缺失、冲突、漂移或 guardian 无法 strict-realpath 证明时不会取得 mutation authority。swap 后失败保持服务收容并保留 current/original home 与 transaction evidence，不把已经迁移的状态自动回滚或重放。

preview 使用 fresh UUID 和新 package catalog，在 no-network bubblewrap 中运行；它唯一允许的 process-local external-provider exemption 是禁用 `larkChannel` 并从 preview Health required providers 移除该项，active 配置不得继承 exemption。真实 service 验收要求 fresh InvocationID/journal ready marker、required Lark health、严格前进且精确匹配 active 配置的 attestation，以及稳定窗口。这里的组合和生命周期语义按本仓实际 `@deepseek-ai/cordis@4.0.2`、Loader `1.0.3`、Include `1.0.7` 验证；sibling Cordis checkout 只用于解释 Fiber、injection、effect ownership 和 Loader composition。

supervised uninstall 只停用目标 profile 的本地受管能力：事务停止并收容经证明归属该 canonical home 的 unit，归档目标 profile 的完整目录树，再用 installer-clean 的同名 Web profile 替换 live target。clean target 不再要求 Lark、Health 或 supervised active attestation，只通过 fresh InvocationID、对应 journal ready marker 和稳定窗口组成的通用 readiness；原 active unit 恢复，原 inactive unit 保持停止。uninstall 不访问 npm registry 或 pnpm store，也不撤销凭据、owner binding、Session、Goal、数据库或其它共享/外置状态。完整 profile-tree 归档不等于整个 home 的逐字节证明，后续重装或共享同一状态库的其它 profile 仍可能解释这些保留状态。

DSH 尚处于预发布阶段，插件机制可能发生破坏性变化。`pnpm-workspace.yaml` 的 catalog 和各插件 `peerDependencies` 是实际依赖范围的源；本页记录人工验证过的 DSH 基线。

升级基线时：

1. 阅读上游插件打包、profile、Cordis 生命周期和相关 subsystem 文档。
2. 更新 catalog 与所有受影响的 peer 范围。

4. 用目标 DSH 的 `--dump-config` 验证每个 bundle，再做真实 profile 冒烟。
5. 在本页记录新的已验证版本，并在插件 README 中说明任何功能差异。

Delivery Session 排他按同一 `0.1.2-rc.1` AgentLoop factory 的实际生命周期接线：setup/发布失败会 await 内部 teardown 后抛出；成功 handle 的 dispose 等待 machine idle、异步 scope 清理和 unregister。插件仍独立跟踪在途流/工具，不能仅凭 registry 移除或超时判断已清理。升级 Host 时需重跑失败 setup、取消、挂起工具/流、迟到调用、双连接竞争、新 Session orphan 归属及 `/new` 冷恢复用例。Delivery schema 20 不提供对已打开的旧 writer 的运行时兼容排他，部署前须排空旧 Host。

Web Session 排他回归使用 `@deepseek-ai/dsh-api-session-controller@0.1.2-rc.1` 的真实 `SessionController`，并在根开发依赖固定同版本的 AgentDefaultModel、SessionQuery 和 TypertRegistry；它们不作为 Delivery 的新运行时依赖发布。实际 `follow()` 在冷快照 yield 后通过原生 AgentLoop 恢复 Session，`prompt(request, signal)` 既能借用这个新 Agent，也能借用正在执行的同一 Agent。Delivery 通过持久归属检查拒绝前者，通过原生 `agent/inbox/inserted` / `claimed` 的 direct-user 输入取消后者的租约；不能把消息来源标签当作对任意 Host 插件的隔离。升级时必须重跑 cold follow、live prompt 取消后不重放、普通未托管 Web Session 正常执行三项回归。

上述测试直接调用生产 Controller 与 Session persistence coordinator，模型为确定性 adapter，未验证浏览器认证、HTTP/WS 传输或完整 Web owner 产品入口。取消 Agent 不会自动释放 Web Controller 持有的会话生命周期，因此取消后不能假定 Delivery 已能重新取得该 Session。当前 Web 的身份关联、恢复准入和 teardown 还需一起接入；仅替换 create/prompt/cancel 无法覆盖内部历史恢复和 Typert Agent lookup。

共享 factory 生命周期依赖同一版本 `CreateAgentOptions.setup` / `ResumeAgentOptions.setup` 的 `AgentSetupCommit`、原生回滚等待及 memoized `AgentHandle.dispose()`。Delivery 包装器在 setup 内绑定 lease，并在调用方 commit 前后重查；冷加载也计为在途。通过 `ownerCtx.reflect.trace()` 调用共享原始 registry，保留调用方 owner fiber，支持后续在 Controller 构造处提供限定作用域的 registry facade，不能创建第二个 AgentRegistry/factory。调用方卸载时额外 await 原生 disposer；不根据 `agent/disposed` 通知单独推断 quiescent。此 seam 目前仍为内部实现，未向普通 Web 请求开放 owner 授权。

特别注意原生 `resumeWith()` 的 `raceAbortCall()`：调用方、owner fiber 或 factory 取消可先拒绝公开 resume Promise，未合作的 `persistence.prepare()` 可在之后返回并由上游 dispose。公开 API 不提供区分错误来源和观察该迟到清理的凭证。包装器通过 Cordis 同步 `internal/service` 通知跟踪 `agentLoop` 有效代次，并在错误返回时核对同代原生 provider 仍可见、调用方 `FiberState.ACTIVE`、组合 signal 未取消；只有排除 rc.1 的全部三条取消路径，才能把普通加载错误作为已结束的 load。provider 消失/替换、调用方卸载、signal 取消或非原生 factory 无法提供该证明时，保留 unknown；迟到 preparation 的清理不会自动解锁。setup 已收到 Agent 后的失败仍依赖原生等待 Agent rollback 的契约。升级 Cordis/AgentLoop 必须重查同步服务代次通知、三个取消来源与错误返回时序，不能靠错误消息猜测。

construction 自身的 owner effect 把卸载记入不可复位的组合取消信号；即使同一 fiber 很快重启并再次 ACTIVE，也不能清除旧构造的取消。`FiberState` 在 Cordis 4.0.2 发布物中是擦除的 const enum；实现用对应成员类型约束数值，避免转译器尝试读取不存在的运行时导出，升级时类型检查必须继续核对该值。

上述 factory 代次证明限定于官方 AgentLoop 向当前 AgentRegistry 注册 factory 的标准生命周期；其 setFactory effect 随 provider fiber 清理。AgentRegistry 没有公开私有 factory 槽的变更通知，不宣称追踪任意 Host 代码脱离该生命周期更换 factory 的行为。

Skills 的 qualified canary revision monitor 还需要同批 Evaluation Host 服务提供 `getTrustedGoalOutcomeLearningProjection`、`withTrustedCanonicalTaskWriterFence` 和 `onTrustedTaskChange`。lookup 只按 canonical workspace/preset 与 assessment ID 返回 exact `goal-outcome` current projection；canonical task fence 同步核对 scope watermark、subject kind/ref、revision、digest 及 `upsert | retract`，且不等待 Evolution outbox。旧 Evaluation 或 provider 暂时缺失时，普通手工 skills 与 standalone observation watch 保持原契约，但 qualified deployment 必须在 claim/dispatch 前 fail closed，不能退回只信 immutable Verifier receipt。

Evaluation 在 Cordis optional injection 出现时建立 task-change subscription，provider replacement 会先清理旧订阅，再由新 provider 触发 cold reread；通知只作 nudge。Skills 持久化第一次 Goals/Verifier/run/task-family binding，后续只允许同 assessment 的严格前进 canonical revision 替换或撤回，并在 Evaluation writer fence 内把 Skills observation/deployment/rollback 作为一个同步 writer transaction 提交。新 qualified watch 使用 `canonical-goal-outcome/v2`；旧版或畸形 active qualified deployment 缺少 exact canonical evidence 时在打开 Store 时 fail closed 为 blocked，不能从旧 receipt 猜测或回填可信 revision。升级 Evaluation 或 Skills 时必须成套重跑 provider unload/replacement、启动恢复、相同 revision 幂等、并发 revision、retract 不复活，以及 deployed run 的 pre-claim/post-reservation/per-dispatch gate。当前 standalone watch 不迁移为 canonical monitor。

whole-goal owner feedback 要求 Goals、Delivery 与 Evaluation 同批升级；三者互相消费这组新 ABI 的 peer 下界均为 `>0.1.24 <0.2.0`，即正常正式版本至少 `0.1.25`。Goals 暴露 `assistant-goals/owner-goal-outcome-feedback/v1` 的 process-local capability，Delivery schema 20 把 exact locator/proof sidecar 与外部 result Outbox 原子写入，Evaluation Delivery producer 必须发布 `owner-objective-revision/v2`。发送前 Delivery 通过当前 Goals provider 重建 proof，并重验 Verifier receipt freshness、owner route/binding/Session 与 exact Policy；provider replacement、route 漂移或过期 proof 在 adapter I/O 前 fail closed。结果已取得 provider message id 后，同一 owner 可回复原消息使用现有 `/feedback status|correct|withdraw`；历史 receipt 允许过期，但每次仍由当前 Goals/Verifier 重验不可变 Goal definition、assessment、run、profile、contract 与 receipt identity，再由 Evaluation 执行 baseline adoption、version/status CAS 和 retract。旧 Evaluation 不得把 whole-goal 降级为 v1 或独立评价票。

Lark 不增加领域 authority，只转发已有 provider reply identity；其 adapter 可与 Delivery/Goals/Evaluation 分批发布，但完整产品路径只有同批 Host ABI 生效。Web `native-session` 不生成 external Outbox/provider reply identity，当前明确不支持这条路径。仓库测试使用本地 transport 和 Host fixture，不能冒充真实 Lark、真实模型或生产 owner/canary cohort。canonical monitor 仍只覆盖 qualified finite canary，未证明其它 deployment cohort、生产 rollout 或真实模型收益。升级必须重跑 Delivery v19→v20 迁移、sidecar/Outbox 原子性、发送前过期/provider/route/Policy 拒绝、重启后 exact reply、错消息/错 owner、历史 receipt 到期后的 identity revalidation、CAS conflict/replay/retract 以及 Skills rollback。

Prospective holdout profile 现有三个任务族：order-summary（v1/v2）、template-render/v1 与 dependency-topological-order/v1。第三族的 wire identity、generator/profile digest、冻结后私有 dataset、Ed25519 certificate、qualification/admission 和恢复状态必须精确匹配；旧 reader 不得把未知 profile 当成 order-summary。已消费或已冻结 authority 不能通过改 generator 重开资格，冻结后失败也不能重新抽样。topology v1 的有效 label 是 `[a-z][a-z0-9]{1,31}`，DAG 使用每步 min-lex ready node，cycle 输出 `CYCLE\n`；任何语义变化都需要新 profile/version 与新 digest，不能原地改 v1。
